\section{Methodology}

\subsection{Study Design and Data Source}
The dataset used in this study corresponds to the COVID-19 severity assessments collected for this research. Records were collected from patients evaluated through the COVID-19 assessment workflow, and each record contains demographic variables, comorbidities, symptom profiles, and exposure-related information. Only complete assessments with a confirmed severe or non-severe label were included. A total of 393 assessments met these criteria and were used in all analyses. All data were de-identified, and the study protocol followed the ethical guidelines established for the data collection.

\subsection{Dataset Description}
The dataset used in this study consists of structured COVID-19 clinical assessments containing demographic information, medical history variables, symptom profiles, and exposure-related features. These variables were selected to represent key risk factors associated with clinical deterioration and were aligned with features commonly used in COVID-19 severity stratification literature. The target outcome is a binary classification indicating whether the patient experienced a severe or non-severe clinical course. Severity labels followed the definition established in our prior pediatric COVID-19 study, where outcomes were determined using chart review and thirty-day follow-up surveys \cite{hicks2023saliva}.

The dataset contains the feature groups shown in Table 1, including demographic variables (such as age group and sex), comorbidities (such as diabetes, cardiovascular disease, and chronic lung disease), symptoms (such as fever, dyspnea, chest pain, sore throat, anosmia), and exposure history. All features were converted into binary or categorical encodings consistent with the schema described in the paper. Missing symptom responses were treated as symptom absence to match the data collection format.

The 393 assessments were split into training, validation, and test sets following the standard procedure: 70\% training, 10\% validation, and 20\% testing. The same test set was used for evaluating all ML models and all LLM variants to ensure a consistent comparison. These partitions were used to train and evaluate the traditional machine learning models described in Section 3.2 and to provide ground truth comparisons for LLM outputs. \subsection{Machine Learning Baselines}
To benchmark the LLM-based system against traditional approaches, three supervised machine learning classifiers were implemented: logistic regression, random forest, and XGBoost. These methods were chosen because they represent widely used baselines for structured clinical prediction tasks and provide a comparison point for evaluating the utility of generative LLMs in risk stratification.

Model training followed the procedures described in the paper, using the same dataset partitions and ensuring that each model received the same structured feature inputs as the LLM. Hyperparameters were tuned using grid search on the validation partition. Performance was evaluated on the held-out test set using accuracy, precision, recall, F1-score, and AUC, matching the evaluation criteria reported in the original study. We used Shapley additive explanations (SHAP) to interpret XGBoost predictions, following the unified framework proposed by Lundberg and Lee \cite{lundberg2017unified}.

These ML models serve as reference points to contextualize the performance of the LLM-based approach described below. Because the severe class was underrepresented, stratified splitting was used to preserve class proportions across the train, validation, and test partitions.

\subsubsection{Conversational Assessment Flow}
The system uses an interactive question–answer workflow in which the application presents a sequence of clinically relevant questions to the user. These include demographic questions, medical history items, exposures, and symptom queries. Each user response updates an internal structured representation of the assessment. An example of the assessment question–answer interface used to collect user responses is shown in Figure~\ref{fig:interface_views} (Assessment View).

This conversational design ensures that all necessary risk factors are collected while allowing users to respond naturally. The assessment uses a structured sequence of predefined questions, and the LLM generates risk predictions and explanations based on the collected information.

An example of the assessment question–answer interface used to collect user inputs is shown in Figure~\ref{fig:interface_views} (Assessment View).

\subsubsection{Serialization of Structured Features}
Once the assessment is complete, the structured variables are serialized into a textual format that the LLM can interpret. The serialization template mirrors the one described in the paper and encodes each variable as a labeled key–value pair (e.g., “Age group: 40–49”, “Has diabetes: No”, “Experiencing shortness of breath: Yes”). This ensures that the model receives a deterministic representation of the patient profile.

The serialized prompt instructs the LLM to output:
\begin{itemize}
    \item A numerical probability indicating risk of severe COVID-19
    \item A natural-language explanation summarizing the contributing factors
\end{itemize}
We fine-tuned the base LLMs on a small labeled dataset of serialized assessments using both list-style and text-style templates. At inference time, the patient's serialized feature vector is formatted using the same template and submitted to the fine-tuned LLM to obtain a risk probability and explanation.

Two serialization formats were used, consistent with our pipeline:
\begin{itemize}
    \item \textbf{List serialization (-L):} Each feature is represented as a bullet-point-style entry, e.g., ``$\bullet$ Age group: 40-49; $\bullet$ Diabetes: No; $\bullet$ Fever: Yes.''
    \item \textbf{Text serialization (-T):} Feature--value pairs are integrated into a paragraph-style textual description.
\end{itemize}
Both formats were used for fine-tuning and evaluation, and later performance comparisons (Chapter 4) distinguish results for the two serialization types.

\subsubsection{Model Training Configuration}
Consistent with our pipeline, we fine-tuned multiple LLMs on serialized assessments. The models included T0pp, Flan-T5-XL, and BioMedLM variants. Training was performed using low-rank adaptation (LoRA) to reduce memory usage. Each model was fine-tuned separately using both list-style and text-style serialized datasets. The fine-tuning dataset consisted of the 393 assessments, and training was run for a small number of epochs with a learning rate in the range reported in the original study. Evaluation was performed on the same held-out test set used for the ML baselines.

\subsubsection{Prompt Template and Output Format}
The prompt includes an instruction block followed by the serialized features. The instruction clarifies the task (risk estimation), the expected output format (probability followed by explanation), and constraints preventing the model from offering diagnostic guidance.

The LLM returns a probability score and a rationale that describes the dominant features influencing the output. These outputs are parsed and prepared for downstream display in the user interface.

\subsubsection{Probability Computation and Decision Rule}
For each serialized input \( S_i \), the fine-tuned LLM outputs logits corresponding to the \texttt{yes} and \texttt{no} classes. The probability of a severe outcome is computed using the binary softmax function:
\[
p(\text{yes} \mid S_i) = 
\frac{e^{\text{logits}_{\text{yes}}}}
{e^{\text{logits}_{\text{yes}}} + e^{\text{logits}_{\text{no}}}}.
\]

The final binary prediction is obtained using a threshold of 0.5:
\[
\hat{y}_i =
\begin{cases}
1, & \text{if } p(\text{yes} \mid S_i) > 0.5, \\
0, & \text{otherwise}.
\end{cases}
\]

\subsubsection{Risk Interpretation and Display}
Predicted probabilities are mapped into categorical risk levels following the thresholds established in the study design:
\begin{itemize}
    \item \textbf{Low risk:} \( p < 0.33 \)
    \item \textbf{Moderate risk:} \( 0.33 \leq p < 0.67 \)
    \item \textbf{High risk:} \( p \geq 0.67 \)
\end{itemize}
These categories are displayed in both the Patient interface and Clinician interface. Explanations are also displayed to enhance interpretability and transparency, accompanying the numerical score on both the patient and clinician interface pages.

\subsubsection{Backend Architecture}
The backend consists of:
\begin{itemize}
    \item A cloud-based LLM inference service
    \item Firebase for data storage and retrieval
    \item Secure API endpoints connecting the app and backend
\end{itemize}
The architecture supports real-time communication between the mobile frontend and the LLM backend.

The mobile app was implemented using Flutter, and the backend inference service was deployed using Python and FastAPI. All communication between the app, backend server, and Firebase database occurs over encrypted HTTPS connections. The LLM inference server is containerized and hosted on a secure cloud instance as described in the system documentation.

\subsubsection{Security and Data Handling}
The system does not store any personally identifiable information. All communication is encrypted, and data stored in Firebase consists exclusively of encoded assessment results. No data is reused for training.

\subsection{Evaluation Setup}
Evaluation consisted of:
\begin{itemize}
    \item Comparing LLM predictions with ML baselines
    \item Assessing explanation consistency
\end{itemize}
The LLM predictions were evaluated using the structured test set, where serialized patient profiles were submitted to the LLM and predictions were compared with ground truth labels. The evaluation mirrors the methodology described in the original paper.

All LLM evaluations used deterministic decoding with temperature = 0 to eliminate sampling variance. This ensures that repeated evaluations of the same serialized input yield identical outputs.

All evaluations used the same partitions and criteria as described in the paper.
